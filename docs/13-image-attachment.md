## 技術調査（13-1）

2026-10-26、Ollama 0.40.5・64GB の Apple Silicon Mac で確かめた。

### Ollama の API

`/api/chat` のメッセージに `images`（Base64 の文字列の配列。`data:` の接頭辞なし）を付ける。

```json
{ "role": "user", "content": "この画像は何？", "images": ["iVBORw0KGgo..."] }
```

### モデルが画像に対応しているか

`POST /api/show` の `capabilities` に `vision` が含まれるかで分かる（`/api/tags` には含まれない）。

| モデル | `capabilities` |
|---|---|
| `qwen3.8:27b`（既定） | `completion` / `vision` / `tools` / `thinking` |
| `qwen2.5:0.5b`（E2E） | `completion` / `tools` |

対応していないモデルへ画像を送ると、Ollama は **400** と `{"error":"Multimodal data provided, but model does not support multimodal requests."}` を返す。

### 形式

PNG・JPEG・GIF・WebP はどれも受け付けた（64×64 の画像で、どれも 83 トークン・約 0.9 秒）。

### 解像度と処理時間

**画像のトークン数は解像度にほぼ比例し、大きい画像は応答までの時間を大きく延ばす**（`qwen3.8:27b`、`think: false`、読み込み済み）。

| 解像度 | 画像を含むプロンプトのトークン数 | 応答までの時間 |
|---|---|---|
| 64×64 | 84 | 0.9 秒 |
| 1280×720 | 899 | 7.9 秒 |
| 1536×864 | 1,315 | 11.8 秒 |
| 1920×1080 | 2,059 | 19.2 秒 |
| 3840×2160 | 8,179 | 94.7 秒 |

Retina の画面のスクリーンショットはそのままだと 3,000px を超えることが多い。そのまま送ると 1 枚で 1 分以上待たされるため、**ブラウザで縮小してから送る**（[画像の前処理](#画像の前処理ブラウザ)）。

### 履歴の画像とプロンプトのキャッシュ

Ollama は前回と先頭が同じプロンプトを再評価しない（同じ画像を含む 2 回目の質問は 0.4 秒で返った）。ただし**このアプリはシステムプロンプトに分単位の現在の日時を入れる**（#154）ため、送信のたびに先頭が変わり、履歴の画像も毎回評価し直しになる。履歴の画像を全部送り続けると、画像が増えるほど応答が遅くなる。そのため LLM へ渡す画像の枚数に上限を設ける（[LLM へ渡す画像の選び方](#llm-へ渡す画像の選び方)）。

> キャッシュが効くように日時の置き場所を変えるのは、画像に限らない改善のため別の issue とする。

## 方針の決定

### 画像の保存先: DB の専用テーブル（`bytea`）

| 観点 | 専用テーブル・`bytea`（採用） | `Message.metadata` に Base64 | ファイルに保存 |
|---|---|---|---|
| 会話の削除 | `onDelete: Cascade` で一緒に消える | 一緒に消える | ファイルを別に消す処理が要り、取り残しが出うる |
| メッセージ一覧の取得 | 画像の中身を含めず軽いまま | 画像の中身ごと返り、1 会話で数十 MB になりうる | 軽いまま |
| 大きさ | 元のバイト数 | Base64 で約 1.33 倍 | 元のバイト数 |
| バックアップ | DB のボリュームだけ | DB のボリュームだけ | DB とファイルの 2 か所 |

localhost の個人利用で、画像は縮小してから保存するため 1 枚あたり数百 KB〜数 MB に収まる。DB に置いても困らず、削除の整合と一覧の軽さを両立できる専用テーブルを採る。

### 画像を LLM へ渡す経路: ID で送り、サーバーが DB から読む

`/api/chat` には画像の中身ではなく**添付の ID** を送り、Route Handler が DB から読んで Base64 にして Ollama へ渡す。

- user メッセージは `/api/chat` を呼ぶ前に保存済み（`useChat` の既存の流れ）のため、送信した画像も ID で参照できる。
- 履歴の画像をブラウザが毎回送り直さずに済む（再読み込みした会話では、ブラウザは画像の中身を持っていない）。
- 再生成（#9）も、対象の質問の添付 ID を送るだけで画像付きで作り直せる。

これにより `/api/chat` が初めて DB を読む。読むのは添付だけで、会話・メッセージには触れない。

### 添付の ID: ブラウザが採番する

メッセージの ID と同じく（#9）、添付の ID もブラウザが `crypto.randomUUID()` で採番して保存 API に渡す。保存の応答を待たずに、同じ ID で `/api/chat` を呼べる。保存の再試行で同じ ID が再送された場合は、メッセージと同じく 409 を成功扱いにする。

## データフロー

```
📎 添付（ファイル選択 / ドラッグ＆ドロップ / 貼り付け）
    ↓ ブラウザで検証・縮小・再エンコード（EXIF を落とす）
🖼 プレビュー（data: URI）・削除
    ↓ 送信
💾 POST /api/conversations/[id]/messages   … user メッセージと画像（Base64）を 1 トランザクションで保存
    ↓ 保存成功
📤 POST /api/chat   … message + imageIds、履歴の各要素にも imageIds
    ↓ Route Handler: 添付を DB から読む → モデルの vision を確認 → Base64 にして images へ
🤖 Ollama → ストリーミング応答（既存のまま）
    ↓
💬 チャット画面: 送ったばかりの画像は手元の data: URI、復元した画像は GET /api/attachments/[id]
```

## DB

```prisma
model Message {
  // ...既存の項目
  attachments Attachment[]
}

model Attachment {
  id        String   @id @default(uuid())
  messageId String
  message   Message  @relation(fields: [messageId], references: [id], onDelete: Cascade)
  position  Int      // メッセージ内の並び順（0 始まり）
  mimeType  String   // 中身から判定した形式（image/png・image/jpeg）。クライアントの申告は使わない
  width     Int
  height    Int
  size      Int      // バイト数
  data      Bytes
  createdAt DateTime @default(now())

  @@index([messageId])
}
```

- Conversation → Message → Attachment の順でカスケード削除される。
- `position` を持つのは、同じトランザクションで作った行は `createdAt` が同じになり、並び順を決められないため。
- 添付を持てるのは user メッセージだけ（保存 API で検証する）。

## API

### 変更: `POST /api/conversations/[id]/messages`

ボディに `attachments` を足す（任意。user のときだけ指定できる）。

```json
{
  "id": "…", "role": "user", "content": "このエラーの原因は？",
  "attachments": [
    { "id": "…", "data": "iVBORw0KGgo…", "width": 1280, "height": 720 }
  ]
}
```

- `data` は `data:` の接頭辞なしの Base64。サーバーで復号し、**先頭のバイト（マジックナンバー）で PNG / JPEG を判定**して `mimeType` を決める。どちらでもなければ 400。
- 検証: 枚数・1 枚のバイト数・`width` / `height` の範囲（1〜`MAX_IMAGE_LONG_EDGE`。表示の枠の確保にだけ使う）・ID の UUID 形式・role が user であること。違反は 400。
- メッセージと添付は 1 トランザクションで作る（片方だけ残らない）。

### 変更: `GET /api/conversations/[id]/messages`

各メッセージに、中身を含まない添付の情報を足す。

```json
{ "id": "…", "role": "user", "content": "…", "attachments": [
  { "id": "…", "mimeType": "image/png", "width": 1280, "height": 720 }
] }
```

### 追加: `GET /api/attachments/[id]`

画像の中身を返す。

- `Content-Type`: 保存した `mimeType`（中身から判定したもの）
- `Cache-Control: private, max-age=31536000, immutable`（添付は作った後に変わらない）
- `X-Content-Type-Options: nosniff`
- 不正な UUID は 400、存在しなければ 404

### 変更: `POST /api/chat`

ボディに `imageIds`（送信する質問の添付 ID）を足し、`conversationHistory` の各要素にも `imageIds` を許す（どちらも任意）。

1. ID の形式・枚数を検証する（400）。
2. 画像を渡す場合、モデルが `vision` に対応しているかを確かめる（[画像に対応していないモデル](#画像に対応していないモデル)）。
3. [LLM へ渡す画像の選び方](#llm-へ渡す画像の選び方)で選んだ添付を DB から読む。見つからない ID は 400。
4. Base64 にして各メッセージの `images` に入れ、Ollama へ送る。通常モード・エージェントモードとも同じ。

`OllamaChatMessage` に `images?: string[]` を足す。エージェントループは受け取ったメッセージをそのまま Ollama へ渡すため、変更は要らない。

### 変更: `GET /api/models`

画面で添付の可否を案内するため、モデルごとに画像に対応しているかを返す。

```json
{ "models": ["qwen3.8:27b", "qwen2.5:0.5b"], "visionModels": ["qwen3.8:27b"], "defaultModel": "qwen3.8:27b" }
```

- `lib/llm/ollama.ts` に `getModelCapabilities(model)`（`/api/show` を呼ぶ）を足す。一覧ではモデルごとに並列に呼ぶ。
- `/api/show` が失敗したモデルは「対応していない」とみなさず、`visionModels` から外すだけにする（一覧の取得自体は失敗させない）。
- 既存の `models` の形は変えない（後方互換）。

## 画像の前処理（ブラウザ）

添付した時点で、ブラウザで次の処理をする（`lib/chat/image-attachment.ts`）。

1. **受け付ける形式**: `image/png`・`image/jpeg`・`image/webp`・`image/gif`。それ以外は添付せず、理由を表示する。
2. **元のファイルの上限**: 20MB。超えたら添付しない（縮小の処理でブラウザが重くならないように）。
3. **縮小**: `createImageBitmap` で読み、長辺が 1,280px を超えるときだけ長辺 1,280px に縮小する（[解像度と処理時間](#解像度と処理時間)。1 枚 約 900 トークン・約 8 秒に収める）。
4. **再エンコード**: 元が JPEG なら JPEG（品質 0.9）、それ以外は PNG にする。GIF は最初のフレームだけになる。
   - 縮小が要らない画像も必ず再エンコードする。**EXIF（撮影場所の GPS 等）を落とす**ため。向きは `createImageBitmap` が EXIF の向きを反映してから描くため崩れない。
5. **再エンコード後の上限**: 5MB。超えたら添付しない（1,280px の PNG で超えるのは稀）。

縮小の寸法の計算・形式の選択・上限の判定は純関数にして UT で確かめる。

## LLM へ渡す画像の選び方

- 送信する質問の画像は必ず渡す（最大 4 枚）。
- 履歴の画像は、**新しいものから合計 8 枚まで**（送信する質問の分を含む）を渡す。
- 枚数から外れた画像は渡さず、その履歴の本文の末尾に `（画像 n 枚を添付。古いため省略）` を足す。モデルが「画像があった」こと自体を知らずに答えるのを防ぐ。
- 選び方は DB に触れない純関数にして（サーバー専用のため `lib/server/`）、UT で確かめる。

## 画像に対応していないモデル

- **画面**: 選んでいるモデルが `visionModels` に無いとき、添付した画像のプレビューに「選択中のモデル（`qwen2.5:0.5b`）は画像に対応していません」と出し、**画像を添付している間は送信ボタンを押せなくする**。添付の操作自体は止めない（モデルを切り替えれば送れるため）。
  - モデル一覧の取得に失敗している場合は判定できないため、案内を出さずに送らせる（サーバーで弾く）。
- **サーバー**: `/api/chat` で画像を渡す場合だけ `getModelCapabilities` で確かめる。
  - 送信する質問に画像があり、モデルが対応していなければ **400**（`選択中のモデル（…）は画像に対応していません`）。Ollama の 400 を 502 として返さない。
  - 履歴にだけ画像があり、モデルが対応していなければ、画像を渡さずに本文へ `（画像 n 枚を添付。このモデルは画像に対応していないため省略）` を足して続ける。画像を含む会話の途中でモデルを切り替えても、その会話を続けられるようにする。

- **表示**: user のメッセージの本文の上にサムネイル（高さ 120px 程度）を並べる。送ったばかりの画像は手元の data: URI、会話を開き直した後は `/api/attachments/[id]` で表示する。
- **書き出し**: Markdown・JSON の書き出しには画像を埋め込まず、`[画像 n 枚]` と注記する。

## 上限値

`lib/shared/validation.ts` に足し、画面と Route Handler が同じ定数を使う（`error-handling.md`）。

| 定数 | 値 | 根拠 |
|---|---|---|
| `MAX_IMAGES_PER_MESSAGE` | 4 | 1 枚 約 8 秒。4 枚で 30 秒程度に収める |
| `MAX_IMAGES_PER_REQUEST` | 8 | 履歴の画像も毎回評価し直しになるため（[履歴の画像とプロンプトのキャッシュ](#履歴の画像とプロンプトのキャッシュ)） |
| `MAX_IMAGE_LONG_EDGE` | 1,280px | [解像度と処理時間](#解像度と処理時間) |
| `MAX_IMAGE_BYTES` | 5MB | 再エンコード後の 1 枚。保存 API の検証にも使う |
| `MAX_IMAGE_SOURCE_BYTES` | 20MB | 元のファイル。ブラウザでの縮小の負荷を抑える（画面だけで使う） |

保存 API のボディは最大で 4 枚 × 5MB の Base64 ≒ 27MB になる。Next.js の Route Handler にはボディの大きさの上限が無い（proxy を使っていない）ため、上の検証が上限になる。

## セキュリティ

- **形式はサーバーが中身で決める**: クライアントの申告した形式は使わず、マジックナンバーで PNG / JPEG だけを受け付ける。SVG（スクリプトを含みうる）は受け付けない。
- **配信**: `GET /api/attachments/[id]` は判定済みの `Content-Type` と `X-Content-Type-Options: nosniff` で返し、ブラウザに形式を推測させない。
- **CSP**: 表示は `img-src 'self' data:` の範囲（プレビューは data: URI、復元は同じオリジンの URL）で足り、変更は要らない。`blob:` の URL は使わない。
- **EXIF**: ブラウザで再エンコードして撮影場所などを落としてから送る（[画像の前処理](#画像の前処理ブラウザ)）。
- **ID の推測**: 添付の取得 API と `/api/chat` の `imageIds` は、添付がどの会話のものかを確かめない（認証なしの localhost の個人利用で、会話の境界に意味が無いため。`docs/05-security.md`）。ID は UUID のため推測しにくい。

## やらないこと

- **画像だけの送信**: 本文を必須のままにする。本文が空だとタイトルの生成と会話一覧の表示に別の扱いが要るため、必要になってから足す。
- **画像以外のファイル**（PDF 等）: RAG（#17）の範囲。
- **書き出しへの画像の埋め込み**: 注記だけにする。
- **システムプロンプトの日時の置き場所の見直し**（キャッシュを効かせる）: 画像に限らない改善のため別の issue にする。
