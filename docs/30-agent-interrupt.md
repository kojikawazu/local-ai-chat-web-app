# 応答の途中の指示（割り込み）設計書

> 最終更新: 2026-11-03

エージェントの応答（ツールの呼び出し・サブエージェントへの委譲）の途中で、利用者が追加の指示を送り、エージェントが作業を捨てずに方針を直して続けられるようにする設計（#241）。

## 背景

- 生成中の入力欄は「生成を停止」（と Esc）だけで、送信できない。できることは「最後まで待つ」か「止める」の二択
- 止めると、それまでの作業（読んだページ・ツールの結果・サブエージェントの調べもの）を使わずに終わる。サブエージェントに任せた応答（#26）は 1 回の委譲で 2〜5 分かかり、2 つ任せると 10 分前後になるため、間違いに気付いてから止めて頼み直すまでの損が大きい
- #239 の画面を触っていて、プロンプトの間違いに気付いた段階で利用者から直す手段が無いと分かった（#241 の起票の理由）

今ある仕組みのうち、次を使う。

- **応答の途中で利用者の入力を待つ仕組み**: ツールの承認（#148 Phase A2）。`/api/chat` のストリームが承認を待ち、別の API（`/api/agent/approvals/[id]`）が `globalThis` の待ち合わせへ結果を渡す（`lib/agent/approvals.ts`）
- **呼び出しの ID と途中の経過**（#26 Phase B）: 画面はツールの記録を ID で当て、サブエージェントの中の手順も届く
- **ラウンドの区切り**: エージェントループは「Ollama への問い合わせ → ツールの実行 → 結果を履歴に足す」を繰り返す。次の問い合わせの前が、指示を挟める区切り

## 範囲

| 含める | 含めない（[やらないこと](#やらないこと)） |
|---|---|
| エージェントモードの生成中に、入力欄から追加の指示を送る（「割り込む」） | 通常のチャット（ツールなし）での割り込み（止めて送り直すのと変わらない） |
| エージェントが次のラウンドの前に指示を読み、方針を直して続ける（今の作業を捨てない） | 実行中のツール・Ollama の問い合わせを、指示が届いた瞬間に止める |
| サブエージェントに任せている間に届いたら、任せた仕事を早めに切り上げてメインに戻す | 指示をサブエージェントへ直接渡す |
| 応答の中に、送った指示と「反映済み / 次の区切りで読む」を出す・保存する | 送った指示の取り消し・編集 |
| 次の会話の履歴に、途中の指示を含める | 書き出し（HTML・DOCX 等）に途中の指示を出す（使ってから決める） |

## 決めること（レビューの論点）

2026-11-03 のレビューで、I3（本文を書き終えてから答え直す）・I4（サブエージェントはそこまででまとめて戻る）・I7（直前の質問に足す）を推奨どおりに決めた。ほかも推奨どおり。

| # | 論点 | 推奨 | 理由 |
|---|---|---|---|
| I1 | 届け方 | 応答の最初に **`response_started`（応答の ID）** を送り、画面は **`POST /api/agent/responses/[id]/instructions`**（`{ content }`）で指示を送る。サーバーは応答ごとの受け箱（`globalThis`。承認の待ち合わせと同じ置き方）にためる | `/api/chat` のストリームは片方向のため、承認と同じく別の API で届ける。応答の ID を分けると、終わった応答・別の応答に届かない（404） |
| I2 | 反映の区切り | メインのループの**次の問い合わせの前**に受け箱の指示をすべて取り出し、user の発言として履歴に足し、`instruction_applied` を送る。実行中のツール・問い合わせ・承認待ちは止めない | ツールの途中で止めると、結果の無い呼び出しが履歴に残り、作業も捨てる。区切りで読めば、それまでの結果を使って方針を直せる |
| I3 | 最終回答の途中に届いた | ツールを呼ばずに答え終えたラウンドでも、受け箱に指示があれば終わらずに、書いた本文と指示を履歴に足して**もう 1 ラウンド**回す（ラウンドの上限は今までどおり） | 答えを書いている途中で「そうじゃなくて」と気付く場面がいちばん多い。書いた本文は残し、続きで答え直させる |
| I4 | サブエージェントに任せている間に届いた | サブエージェントの「まとめ始める時間」（#26。150 秒）と同じ扱いで、**途中の問い合わせ・中のツールを止めて、ここまでの情報でまとめさせ**、メインに戻す（要約に「（追加の指示でまとめた）」）。メインは次の区切りで指示を読む | 任せた仕事を最後まで待つと数分かかる。打ち切って捨てると調べた分が無駄になる。まとめの問い合わせは思考なしで 30〜60 秒 |
| I5 | 承認を待っている間に届いた | 承認カードはそのまま出し続け（許可・拒否は利用者が選ぶ）、決着の後の区切りで指示を読む | 承認と指示は別の判断。指示を拒否と見なすと、許可するつもりの操作まで止まる |
| I6 | 画面 | エージェントモードの生成中も入力欄から送れる（Enter・送信のボタン「割り込む」。停止のボタンも並べて出す）。送った指示は応答の中に「追加の指示」として出し、読まれる前は「次の区切りで読みます」、読まれたら読んだ位置（本文の位置）に並べる | 送ったのに読まれたか分からないと、また送る・止めるの判断ができない |
| I7 | 次の会話の履歴 | 応答の記録（`metadata.instructions`）に指示と読んだ位置を保存する。次の送信の履歴では、**その応答の直前の user の発言の後ろに「（応答の途中で足した指示）」として足す** | 指示を失うと、次の質問で前提が食い違う。assistant の本文に混ぜると、モデルが自分の発言と取り違える |
| I8 | 停止したとき | 読まれていない指示は応答の記録に「読まれなかった」として残し、入力欄に戻す（そのまま送り直せる） | 送った文が消えると、もう一度打ち直すことになる |

## 流れ

```
画面                         /api/chat（ストリーム）                  /api/agent/responses/[id]/instructions
 │ 送信 ────────────────────▶ response_started { responseId } ──┐
 │                            問い合わせ → ツール …              │
 │ 「割り込む」────────────────────────────────────────────────▶ 受け箱に足す（202）
 │◀── instruction_accepted（画面が自分で出す「次の区切りで読みます」）
 │                            区切り: 受け箱を取り出し、user の発言として履歴へ
 │◀────────────────────────── instruction_applied { instructionId, contentOffset }
 │                            問い合わせ（直した方針で続ける）…
 │◀────────────────────────── done（metadata.instructions）
```

- 委譲の途中に届いたら、受け箱の印を見たサブエージェントがまとめ始め（I4）、委譲の結果が返った後の区切りでメインが読む。
- 本文を書き終えたラウンドの後に受け箱が空でなければ、もう 1 ラウンド回す（I3）。

## サーバー

- **受け箱**（`lib/agent/instructions.ts`）: 応答の ID → `{ items: { id, content }[], onArrive: Set<() => void> }` を `globalThis` に持つ。`registerResponse(id)`・`addInstruction(id, content)`（無ければ `false`）・`takeInstructions(id)`（取り出して空にする）・`hasInstructions(id)`・`onInstruction(id, listener)`（届いたら呼ぶ。サブエージェントのまとめ始めに使う）・`unregisterResponse(id)`（応答の終わりに必ず呼ぶ）。
- **API**: `POST /api/agent/responses/[id]/instructions`。`id` は UUID、ボディは `{ content: string }`（前後の空白を除き 1〜2,000 字）。受け付けたら 202 と `{ instructionId }`、待っている応答が無ければ 404、1 回の応答で 5 件を超えたら 409。
- **メインのループ**（`runAgentLoop`）: 最初に応答の ID を採番して受け箱を作り、`response_started` を送る（エージェントモードだけ）。各ラウンドの問い合わせの前に `takeInstructions` し、1 件ごとに `{ role: 'user', content: '（応答の途中の追加の指示）\n' + 本文 }` を履歴に足し、`instruction_applied`（指示の ID・その時点の本文の文字数）を送る。ツールを呼ばずに答え終えたラウンドの後に `hasInstructions` なら、書いた本文を assistant の発言として履歴に足して続ける（I3）。応答の終わり（完了・エラー・停止）で `unregisterResponse`。
- **サブエージェント**（`runSubAgent`）: まとめ始める signal（`answerBy`）に、受け箱に指示が届いたら abort する signal を足す（`onInstruction`）。理由は「追加の指示」として `limit: 'instruction'` を返し、要約に「（追加の指示でまとめた）」。
- **承認**: 変えない（I5）。

## 画面

- **入力欄**（`ChatBar`）: エージェントモードの生成中は、送信のボタンを「割り込む」にして停止のボタンと並べる。Enter で割り込み、Esc は今までどおり停止。通常のチャットの生成中は今までどおり（送れない）。
- **送る**（`useChat` の `sendInstruction`）: `response_started` で受け取った応答の ID へ送り、応答の記録の `instructions` に `{ id, content, status: 'pending' }` を足す（画面だけの状態）。送れなかったら（404・409・通信の失敗）入力欄に戻してエラーを出す。
- **反映**: `instruction_applied` で `contentOffset` を入れ、`pending` を外す。応答の時系列（`AgentSteps`。#186）に、ツールと同じく本文の位置で「追加の指示」の行を並べる（`buildAgentTimeline` に `kind: 'instruction'` を足す）。読まれる前は応答の下（下の「実行中」の表示の上）に「次の区切りで読みます」と出す。
- **停止**: 読まれていない指示は `status: 'unread'` で記録に残し、本文を入力欄に戻す（I8）。

## 保存と履歴

- 応答の metadata に `instructions: { content, contentOffset?, unread? }[]` を保存する（`buildMessageMetadata`・`parseMessageMetadata` で検証。DB のマイグレーションは要らない）。
- 次の送信の履歴（`toConversationHistory`）: 指示を持つ assistant の発言の直前の user の発言の後ろに `\n\n（応答の途中で足した指示）\n- …` を足す（読まれなかった指示は足さない）。上限（`MAX_MESSAGE_LENGTH`）を超えたら、指示の側を切る。
- 再生成（同じ質問で答え直す）は指示を引き継がない（新しい応答は指示の無い状態から）。分岐（#29）は metadata ごと写す。

## 上限値

| 値 | 上限 | 理由 |
|---|---|---|
| 指示 1 件 | 2,000 字 | 方針を直す一言〜数行。メッセージの上限（10,000 字）より小さくし、受け箱を膨らませない |
| 1 回の応答の指示 | 5 件 | 区切りごとに 1 件ずつ読ませても、ラウンドの上限（既定 10）に収まる |

## セキュリティ

- 受け箱に届けられるのは、ストリームで応答の ID を受け取った画面だけ（ID は UUID で推測できない。localhost の個人利用のため認証はしない。承認の API と同じ扱い）。
- 指示は利用者の発言として履歴に入る（ツールの結果ではない）。外部への持ち出しの規則（#148）は今までどおり（指示で `web_search` を頼んでも、手元を読んだ後なら止める）。

## テスト

| 層 | 正常系 | 準正常系 | 異常系 |
|---|---|---|---|
| UT | 受け箱（足す・取り出す・届いたら呼ぶ・消す）・時系列に指示の行・履歴に指示を足す・metadata の検証 | 読まれなかった指示は履歴に足さない・指示の側を上限で切る・5 件目まで | 知らない応答の ID・形の合わない保存済みの指示を捨てる |
| IT（`/api/chat` と指示の API。Ollama・SearXNG はスタブ） | ツールの実行中に送った指示が、次の問い合わせの履歴に user の発言として入り `instruction_applied` が届く・本文を書き終えた後に届いた指示でもう 1 ラウンド回る・委譲の途中に届いたらサブエージェントがまとめて戻る | 承認を待っている間に届いた指示は、決着の後に読む・6 件目は 409 | 終わった応答・知らない ID は 404・空・長すぎる指示は 400・停止で受け箱が消える |
| E2E | 大きいモデルで調べものを頼み、途中で「日本語の出典だけにして」と割り込むと「追加の指示」が出て反映される（軽量モデルでスキップ） | エージェントモードでないときは割り込めない・保存した応答の指示が時系列に出る（API で入れた記録） | 指示の API の失敗（`page.route`）で入力欄に戻りエラーが出る |

## 実装で分かったこと

- **実際のモデルで、指示どおりに方針を直した**: `qwen3.8:27b` に「Ollama の最近のリリースで何が変わったか調べて」と頼み、最初の検索の開始で「英語のページは読まず、日本語の出典だけを使って、最後に箇条書き 3 行でまとめて」と割り込んだ。次のラウンドの前に読まれ（`instruction_applied`）、モデルは日本語のページだけを開いて、箇条書き 3 行で答えた（応答全体 76 秒）。
- **指示の API の応答より先に「読んだ」知らせが届くことがある**: 指示を入れた直後に区切りが来ると、`instruction_applied` が指示の API の 202 より先にストリームで届く。画面は、まだ知らない指示 ID の「読んだ」知らせを控えておき、API の応答が届いたときに当てる（`useChat` の `appliedEarly`）。
- **同じ位置のツールとの前後**: 指示は「前のラウンドのツールの結果がそろった後・次のツールの前」に読まれるため、本文の位置（`contentOffset`）だけではツールとの前後が決まらない（ツールの前に本文が無いと同じ位置になる）。読んだ時点までに始まったツールの数（`toolCallIndex`）を保存し、時系列で同じ位置のツールの間に並べる。
- **「割り込む」は応答の ID が届くまで押せない**: 送信の直後は応答の ID（`response_started`）がまだ無く、指示の送り先が無い。ボタンは出すが押せないようにした（E2E で `/api/chat` を止めて確かめた）。

## やらないこと

- **通常のチャットでの割り込み**: ツールのラウンドが無く、区切りが無い。止めて送り直すのと同じ。
- **届いた瞬間に止める**: 結果の無いツールの呼び出しが履歴に残り、作業も捨てる。止めたいときは「停止」を使う。
- **サブエージェントへ直接渡す**: サブエージェントは会話を見ない作り（#26）。メインが指示を読み、必要なら任せ直す。
- **送った指示の取り消し・編集**: 読まれる前なら取り消せる形も考えられるが、使ってから決める。
