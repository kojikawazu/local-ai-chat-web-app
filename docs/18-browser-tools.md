## 背景

今の Web のツールは `web_search`（検索結果）と `url_fetch`（HTML の本文）だけで、静的に取れる内容しか読めない。

- JavaScript で描画するページ（SPA）の内容が読めない。
- 画面の見た目を確かめられない。開発中のアプリの動作確認（#148 のツールでコードを直した後に画面を見る）に使いたい。
- `url_fetch` はプライベートの IP アドレス（`localhost` 等）を止めているため、手元の開発サーバーを読めない。

## 前提の調査

Playwright 1.64.1（E2E で使っている版）と `qwen3.8:27b`（Ollama 0.40.5）で確かめた（2026-10-30）。

### スナップショットの大きさ

ビューポート 1280×800 で、`domcontentloaded` の後に取った。

| ページ | 取得の時間 | スナップショット（通常） | スナップショット（`mode: 'ai'`。要素の参照付き） | スクリーンショット（PNG） |
|---|---|---|---|---|
| example.com | 0.8 秒 | 1,047 文字 | 1,176 文字 | 81 KB |
| nextjs.org/docs | 1.4 秒 | 13,975 文字 | 21,732 文字 | 138 KB |
| GitHub のリポジトリのトップ | 1.9 秒 | 25,581 文字 | 41,626 文字 | 92 KB |
| ja.wikipedia.org の記事 | 0.9 秒 | 39,749 文字 | 63,220 文字 | 250 KB |

- 文書の多いページは、そのまま渡すと数万文字になる。入力を読む速さ（1 秒あたり 100〜130 トークン。[14-local-file-tools.md](./14-local-file-tools.md)「前提の調査」）から、上限が要る。
- `mode: 'ai'` は要素ごとに `[ref=e13]` の参照を付け、`aria-ref=e13` でその要素を指せる（クリックで確かめた）。操作（Phase C）の要素の指定に使えるが、文字数が 1.5 倍になる。

### ツールの結果に画像を付ける

`role: 'tool'` のメッセージに `images`（base64）を付けて、合言葉とボタンの文字を書いたページ（1280×800）のスクリーンショットを渡した。

| 渡し方 | 入力のトークン | 答え |
|---|---|---|
| 画像を付ける | 1,329 | 合言葉「ペンギン42」・ボタン「送信する」を正しく読んだ（20 秒） |
| 文章だけ（「スクリーンショットを撮りました」） | 326 | **画面に無い「グレーの円」「Open in new window」を作って答えた** |

- ツールの結果の画像は読める。1280×800 で約 1,000 トークン増える。
- 画像を渡せないのに「撮った」とだけ返すと、モデルは見たふりをする。画像を読めないモデルには、スクリーンショットのツールを渡さない（[スクリーンショットをモデルへ渡す](#スクリーンショットをモデルへ渡す)）。

### リダイレクトの先の判定

許可したポート A・C と、止めたいポート B の 3 つのサーバーを手元に立て、A→B・A→C→B と転送させた。

| 判定のしかた | A→B | A→C→B | ページの中から B への `fetch` |
|---|---|---|---|
| `context.route` で横取りし、通すものは `route.continue()` | **B が読めた** | — | — |
| `route.fetch({ maxRedirects: 0 })` で取り、転送の先を確かめてから `route.fulfill` | 止まった | **B が読めた** | — |
| アプリの中のプロキシにすべての通信を通す（`launch({ proxy })`） | 止まった | 止まった | 止まった |

- `route` は転送の 2 回目以降を通らない。302 を返すとブラウザが自分で先へ進むため、連鎖をすべて確かめられない。
- プロキシなら、転送の先・ページの中のリクエスト・HTTPS（`CONNECT`。暗号は解かず宛先だけを見る）がすべて新しい接続としてプロキシに来る。Chromium は既定でループバックへの通信をプロキシに通さないため、`bypass: '<-loopback>'` で外す（`localhost` もプロキシに来ることを確かめた）。

### Next.js からの読み込み

`playwright-core` は Next.js 16 の `serverExternalPackages` の既定の一覧に入っている。`next.config.ts` を変えずに、Route Handler から読み込める（バンドルされない）。

| 論点 | 推奨 | 他の案 | 理由 |
|---|---|---|---|

| 有効にする設定 | **`BROWSER_ENABLED=true`** で登録する（既定は使わない）。手元の開発サーバーは **`BROWSER_LOCAL_ORIGINS`** に書いたオリジンだけを開ける | 既定で有効（`url_fetch` と同じ）／`BROWSER_ALLOWED_ORIGINS` で公開の Web も含めて許可リストにする | ブラウザは Chromium のインストールとメモリ（数百 MB）が要るため、利用者が選んで使う。公開の Web まで許可リストにすると、SPA を読む使い方がほぼできない。手元のサービス（DB の管理画面・Ollama 等）は明示したものだけを開ける |
| セッションの長さ | **1 回の応答の間だけ**。応答が終わったらページを閉じる | 会話ごとに持ち、一定時間で閉じる | 読み取りだけなら、続きは URL を開き直せば足りる。会話ごとに持つには `/api/chat` に会話 ID を渡し、放置の後始末を作る必要がある。ログインした状態を続ける操作（Phase C）で要るなら、そこで作る |
| 宛先の判定のしかた | **アプリの中のプロキシ**に Chromium の通信をすべて通し、接続ごとに判定する | Playwright の `route` で横取りする | `route` は転送の連鎖をすり抜ける（[前提の調査](#リダイレクトの先の判定)）。プロキシは名前を引いて確かめたアドレスへそのまま接続するため、DNS rebinding も防げる |
| ツールの分け方 | **3 つ**: `browser_navigate`（開いて、スナップショットを返す）・`browser_snapshot`（今のページを読み直す・続きを読む）・`browser_screenshot` | 開くだけのツールと読むツールを分ける | 開いたら読むのがほぼ毎回なので、1 回の呼び出しで済ませる（ラウンドが 1 つ減ると、モデルがそれまでの文脈を読み直す時間が減る） |
| スナップショットの形 | **通常の形**（参照なし）。操作を足すときに `mode: 'ai'` へ変える | 最初から `mode: 'ai'` | 読み取りでは参照を使わず、文字数が 1.5 倍になるだけ。上限の中で読める内容が減る |
| スナップショットの上限 | **12,000 文字**で切り、続きは `browser_snapshot` の `offset` で読む | 上限なし・要約する | `read_file` と同じ上限（約 4,000 トークン・読むのに 30 秒程度）。要約はモデルを 2 回呼ぶことになる |
| 画像を読めないモデル | **`browser_screenshot` をツールの一覧から外す** | 渡したうえで、呼ばれたら失敗を返す | 調査で、画像の無い結果に対してモデルは見たふりをした。渡さなければ呼べない |
| スクリーンショットの表示 | **モデルに渡すだけ**。画面には「撮った」記録（大きさ）だけを出す | 画面にも出す・DB に保存する | 添付画像（`Attachment`）は利用者のメッセージに付く形で、応答の画像の置き場が無い。表示は使ってみて要るなら足す |
| 手元のページを読んだ後 | **手元の開発サーバーのページは `local`**（手元の情報を読む）として扱う。公開の Web を開くのは `network` | ブラウザのツールはすべて `network` | 手元のアプリの画面には非公開の情報が出る。読んだ後に公開の URL を開かせると、URL に載せて外へ送れる（[外部への持ち出しとの関係](#外部への持ち出しとの関係)） |

## 有効にする設定

| 変数名 | 説明 | 既定 |
|---|---|---|
| `BROWSER_ENABLED` | `true` でブラウザのツールを登録する | 未設定（使わない） |
| `BROWSER_LOCAL_ORIGINS` | 開いてよい手元の開発サーバーのオリジン（`http://localhost:5173` の形。カンマ区切り） | 未設定（手元のサーバーは開けない） |

- `BROWSER_LOCAL_ORIGINS` はオリジン（スキーム・ホスト・ポート）で書く。パスが付いていたら警告して外す。`http`・`https` 以外は外す。ポートの省略は既定のポート（80・443）として扱う。
- **このアプリ自身のオリジンは、書いても開けない**（[脅威と対策](#脅威と対策)）。`/api/chat` のリクエストのオリジンを、応答ごとの文脈で渡す。文字列では比べず、**名前を引いたアドレスがループバックで、ポートがアプリと同じ**なら止める（`localhost`・`127.0.0.1`・`[::1]` の書き方の違いですり抜けさせない）。
- Chromium が入っていない（`pnpm exec playwright install chromium` をしていない）ときは、ツールは登録したまま、最初の呼び出しで「使えない」（`toolUnavailable`）を返し、入れ方を伝える。起動時に確かめると、使わないときも起動が遅くなるため。

## ツール

### `browser_navigate`

| 引数 | 必須 | 説明 |
|---|---|---|
| `url` | ✓ | 開く URL（`http`・`https`） |

- [開いてよい URL](#開いてよい-url) で確かめてから開く。`waitUntil: 'load'` で待ち、続けてネットワークが落ち着くのを最大 2 秒待つ（SPA の描画を待つため。落ち着かなくても先へ進む）。
- 結果: 最後の URL（リダイレクトの後）・タイトル・HTTP の状態・スナップショット（先頭から 12,000 文字）。切ったときは、全体の文字数と、続きを `browser_snapshot` の `offset` で読めることを書き添える。
- 要約（画面の 1 行）: `タイトル（ホスト）`。
- HTTP の状態が 4xx・5xx でも、ページが返れば成功として本文を返す（エラーのページの内容がモデルの判断に要るため）。状態は結果に書く。

### `browser_snapshot`

| 引数 | 必須 | 説明 |
|---|---|---|
| `offset` | | 読み始める文字の位置（既定 0）。続きを読むときに使う |

- この応答で開いたページを読み直す（描画を待ってから読む・切った続きを読む）。開いていなければ失敗（「先に `browser_navigate` で開いてください」）。

### `browser_screenshot`

引数なし。今のページの見えている範囲（1280×800）を PNG で撮り、モデルへ画像として渡す（[スクリーンショットをモデルへ渡す](#スクリーンショットをモデルへ渡す)）。ページ全体（`fullPage`）は撮らない（縦に長いページはトークンが大きくなるため）。

## 開いてよい URL

開く URL と、ページが読み込むすべてのリクエスト（画像・スクリプト・`fetch`・リダイレクトの先）を、宛先ごとに判定する。

| 宛先 | 扱い |
|---|---|
| `http`・`https` 以外（`file:`・`data:`・`chrome:`・`javascript:` 等） | 止める（開く URL のとき。ページの中の `data:`・`blob:` の読み込みは止めない） |
| このアプリ自身のオリジン | 止める |
| `BROWSER_LOCAL_ORIGINS` のオリジン | 通す（`local`） |
| 名前を引いたアドレスがプライベート・ループバック・リンクローカル | 止める（`url_fetch` と同じ範囲。判定は `url-fetch.ts` から切り出して共通にする） |
| それ以外（公開の Web） | 通す（`network`） |

- **プロキシで判定する**: Chromium を `launch({ proxy: { server, bypass: '<-loopback>' } })` で起動し、すべての通信をアプリの中の小さい HTTP プロキシ（`127.0.0.1` の空きポート）に通す。プロキシは、`http` はリクエストの URL、`https`・WebSocket は `CONNECT` の宛先（ホスト・ポート）で判定する。HTTPS の中身は解かない。
- **確かめたアドレスへ接続する**: プロキシが名前を引き、引けたアドレスをすべて判定してから、そのアドレスの中から接続する（Chromium には名前を引かせない。接続には、判定したアドレスだけを返す `lookup` を渡す）。判定と接続のアドレスが同じため、DNS rebinding で判定をすり抜けられない。アドレスを 1 つに絞らないのは、`localhost` が `::1` → `127.0.0.1` の順に引け、`127.0.0.1` だけで待ち受ける開発サーバーに `::1` で断られるため（Node が順に試す）。
- 転送（リダイレクト）の先・ページの中のリクエストも、新しい接続としてプロキシに来るため、同じ判定を通る（[前提の調査](#リダイレクトの先の判定)）。
- 開く URL は、ブラウザに渡す前にも同じ判定をする（止める理由をはっきり返すため）。開く URL そのものを止めたときは、理由を結果に書く（「プライベートのアドレスのため開けません。手元の開発サーバーなら BROWSER_LOCAL_ORIGINS に書いてください」）。ページの中のリクエストを止めたときは、プロキシが 403 を返す。
- プロキシは中継するだけで、本文をためない（流したまま渡す）。
- IT で、許可したサーバー A から許可していないサーバー B への転送・A → 許可したサーバー C → B の連鎖・ページの中の B への `fetch`・WebSocket のどれでも、B に 1 度もリクエストが届かないことを確かめた（WebSocket も `CONNECT` でプロキシに来る）。

## ブラウザとセッション

- **ブラウザは 1 つ**: Chromium（ヘッドレス）を最初の呼び出しで起動し、プロセスの中で使い回す（`globalThis` に持つ。承認待ちと同じく、route ごとにモジュールが別に読み込まれても共有するため）。借り手がいなくなってから 5 分使われなければ閉じる。
- **セッションは応答ごと**: 応答の最初のブラウザのツールの呼び出しで、プロキシと、新しいコンテキスト（Cookie・ストレージを持たない）とページを 1 つ作る。プロキシはコンテキストごとに渡す（`newContext({ proxy })`）。判定の決まり（アプリ自身のポート・手元の情報を読んだか）が応答ごとに違うため。応答が終わる（完了・エラー・停止）と、コンテキストとプロキシを閉じて Chromium を返す。同じ応答で並んだ呼び出しは、作成中のセッションを共有する。
- 同時に開くセッションは 2 つまで。超えたら「使えない」ではなく、入力に関係ない一時的な失敗として返す（ほかの応答が終われば使える）。
- コンテキストの設定: ビューポート 1280×800、ロケール `ja-JP`、`acceptDownloads: false`、権限（位置情報・カメラ等）は与えない、`serviceWorkers: 'block'`。
- 新しいウィンドウ（`window.open`・`target="_blank"`）は開かせず閉じる（#200 で、開いたまま操作の対象にするよう変えた。[新しいウィンドウ](#新しいウィンドウ)）。ダイアログ（`alert`・`confirm`）は閉じる。
- 停止・タイムアウト: ツールの `signal` で、開いている読み込みを止める（`page.goto` は signal を受けないため、中断されたらページを閉じる）。ツール全般の上限（`AGENT_TOOL_TIMEOUT_MS`、既定 30 秒）の中で、開く時間の上限は 15 秒にする。

## ツールへ渡す応答ごとの文脈

今のツールは引数と `signal` だけを受け取り、応答をまたいだ状態を持たない。ブラウザのツールは「この応答で開いたページ」を共有するため、エージェントループからツールへ、応答ごとの文脈を渡す。

```ts
type ToolContext = {
  /** このアプリ自身のオリジン（ブラウザで開かせない） */
  appOrigin?: string;
  /** 応答ごとに 1 つ作るものを置く場所（ブラウザのセッション） */
  scope: Map<string, unknown>;
  /** 応答の終わりに後始末を登録する（ブラウザのセッションを閉じる） */
  onDispose: (dispose: () => Promise<void>) => void;
  /** この応答で手元の情報を読むツールが成功したか（プロキシが公開の Web へ接続しないために読む） */
  hasReadLocal: () => boolean;
};
```

- `execute(args, signal, context)` と 3 つ目の引数にする。今のツールは受け取らなくてよい（引数を減らした関数として型が合う）。ループは必ず渡す。ループの外（テスト）から直接呼ぶときは省略でき、ブラウザのツールは失敗を返す。
- ループは、応答の終わり（`finally`）で `onDispose` に登録された後始末を呼ぶ。
- `/api/chat` は `request.nextUrl.origin` を `runAgentLoop` に渡す。

## 外部への持ち出しとの関係

今のループは、手元の情報を読むツール（`access: 'local'`）が成功した後は、外部と通信するツール（`access: 'network'`）を同じ応答の中で止める（[14-local-file-tools.md](./14-local-file-tools.md)「外部への持ち出しを止める」）。ブラウザのツールは、開く先で触れるものが変わるため、`access` を呼び出しごとに決める。

| ツール | 実行の前（止めるかの判定。`access`） | 実行の後（手元を読んだか。結果の `readLocal`） |
|---|---|---|
| `browser_navigate` | 開く URL が `BROWSER_LOCAL_ORIGINS` なら `local`、それ以外は `network` | 開いた後（転送の後）のページが `BROWSER_LOCAL_ORIGINS` なら true |
| `browser_snapshot`・`browser_screenshot` | 付けない（読むだけで外へ送らない） | 今のページが `BROWSER_LOCAL_ORIGINS` なら true |

- `Tool` の `access` に、引数から決める関数も書けるようにする（`ToolAccess | ((args) => ToolAccess | undefined)`。ループの `resolveAccess`）。
- 実行の前の `access` は開く URL だけで決まるため、読み直し・スクリーンショットのように URL を取らないツールでは決まらない。そのため、ループだけが読む `readLocal` を結果に足し、実行の後でも「手元の情報を読んだ」とループに知らせる。
- **公開のページから手元へは接続させない**: 最上位のページが手元の開発サーバーのときだけ、プロキシが手元への接続を通す（`gateByTopPage`）。公開のページの中のスクリプト・iframe・画像が手元の開発サーバーを読み、外へ送ったり、ページに書き出してモデルに読ませたりする経路を止める（開発サーバーは CORS をすべて許可していることが多い）。公開の URL から手元への転送も止まる。最上位のページは、`browser_navigate` で開く前（`prepareNavigation`）と、ページの中の移動（`framenavigated`）で切り替える。公開のページから手元のページへ移るときは、先に `about:blank` へ移って古いページのスクリプトを止めてから切り替える（切り替えた後に古い公開のページが手元へ接続できる隙を作らない。これも自動のセキュリティレビューの指摘）。開けなかったときは、今のページの URL に合わせ直す。手元のページが公開の CDN を読むのは止めない。PR #197 の自動のセキュリティレビューの指摘で足した。
- 手元の開発サーバーのページを読んだ後は、`web_search`・`url_fetch`・公開の Web を開く `browser_navigate` を止める。手元のファイルを読んだ後に、手元の開発サーバーを開くのは止めない（外へ出ないため）。
- **プロキシも止める**: 手元の情報を読んだ後は、プロキシが公開の Web への接続を断る（`ToolContext` の `hasReadLocal`）。手元の開発サーバーから公開の URL へ転送される場合と、すでに開いている公開のページのスクリプトが外へ送る場合も止まる（実装の中で、ツールの判定だけでは届かない経路として足した）。

## スクリーンショットをモデルへ渡す

- ツールの結果に、ループだけが読む `images`（base64 の PNG）を足す（`ToolExecution`。画面・DB へは送らない）。ループは `role: 'tool'` のメッセージの `images` に入れて Ollama へ渡す。
- 結果の文章は「スクリーンショット（1280×800）を画像で渡しました。URL: …」。画面の記録も同じ文章を出す。
- **画像を読めないモデルには渡さない**: ループの最初に、モデルの対応機能（`supportsVision`。#6）を確かめ、対応していなければ `browser_screenshot` をツールの一覧から外す。ツールの定義に `requiresVision: true` を持たせる。
- 画像は同じ応答の中でだけ使う。次の応答で履歴を送るときは、ツールの結果を履歴に入れない今の作りのまま（画像も残らない）。

## 上限値

| 項目 | 値 | 理由 |
|---|---|---|
| スナップショットの 1 回の文字数 | 12,000 文字 | `read_file` と同じ（約 4,000 トークン・読むのに 30 秒程度） |
| ページを開く時間 | 15 秒 | `url_fetch` と同じ。ツール全般の上限（30 秒）の中に収める |
| 描画を待つ時間（ネットワークが落ち着くまで） | 2 秒 | SPA の初回の描画を待つ。落ち着かないページ（ポーリング等）で時間を使い切らない |
| ビューポート | 1280×800 | 画像で約 1,000 トークン（[前提の調査](#前提の調査)） |
| 同時に開くセッション | 2 | 開発機のメモリ（64GB で大きいモデル・Docker と同時に動く） |
| ブラウザを閉じるまでの放置 | 5 分 | 続けて頼むときに起動を待たせない。使わなければメモリを返す |

## 脅威と対策

| 脅威 | 対策 |
|---|---|
| ページの中のプロンプトインジェクション（「この URL を開け」等） | 読み取りだけのため、できることは別の URL を開くことに限られる。手元の情報を読んだ後は公開の Web を開かせない（[外部への持ち出しとの関係](#外部への持ち出しとの関係)）。会話の中の情報を URL に載せて送る経路は `url_fetch` と同じく残る |
| 手元のサービスを読ませる（SSRF。Ollama・PostgreSQL の管理画面・ルーターの設定画面） | プライベートのアドレスは、`BROWSER_LOCAL_ORIGINS` に書いたオリジンだけを開ける。リダイレクトの先・ページの中のリクエストも、プロキシで接続ごとに判定する |
| このアプリ自身を開かせる（会話の一覧の API を読む。Phase C では承認カードを押す） | このアプリのオリジンは、`BROWSER_LOCAL_ORIGINS` に書いても止める |
| `file:` で手元のファイルを読ませる | `http`・`https` 以外は開かせない。ファイルを読むのはローカルのファイルのツール（許可したフォルダ・秘匿ファイルの除外がある）に任せる |
| ダウンロードでファイルを置かせる | `acceptDownloads: false` |
| 利用者のログイン情報を使わせる | 毎回、空のコンテキストで開く（利用者のブラウザのプロファイル・Cookie を使わない） |
| DNS rebinding（判定の後にアドレスを差し替える） | プロキシが名前を引いて判定したアドレスへそのまま接続する（Chromium に名前を引かせない） |
| ほかのプロセスにプロキシを使わせる | `127.0.0.1` の空きポートだけで待ち受け、ブラウザと一緒に閉じる。使われても、通すのは公開の Web と許可したオリジンだけ（ブラウザのツールと同じ範囲） |
| メモリの枯渇 | 同時のセッションの上限、放置で閉じる。プロキシは本文をためない |

## Phase C: 操作のツール

開いたページの要素を、クリックする・文字を入れる・選択欄で選ぶ（#149 Phase C。サブ issue #198）。どの操作も、実行の前に利用者の許可を求める。

### Phase C の前提の調査

Playwright 1.64.1・`qwen3.8:27b`（Ollama 0.40.5）で確かめた（2026-10-30）。フォーム（名前・種別の選択欄・同意のチェック・送信）、押すと先頭に項目が増えるボタン、`confirm` で確かめる削除ボタン、`target="_blank"` のリンクを置いた確認用のページを使った。

**要素の参照（`mode: 'ai'`）**

| 確かめたこと | 結果 |
|---|---|
| 参照の付き方 | `textbox "名前" [ref=e5]` のように、要素ごとに `e` と連番が付く。`aria-ref=e5` でその要素を指せる（入力・クリックで確かめた） |
| 要素が増えた後の参照 | **ずれない**。参照は要素そのものに結び付き、先頭に項目が増えても `e16` は「項目 1」のまま。増えた要素には新しい番号（`e17`・`e18`）が付く |
| 古いスナップショットの参照 | 要素が残っていれば使える（最初のスナップショットの `e10` が、3 回目のスナップショットの後も「送信する」を指した） |
| 名前が変わった要素の参照 | 押すと「押した」に変わるボタンは、同じ要素でも新しい参照（`f1e2` → `f1e4`）になった。古い参照で再び操作するときは読み直しが要る（操作の結果に新しいスナップショットを返すため、モデルは新しい参照を使える） |
| 消えた要素の参照 | 見つからず、操作の待ち時間の上限まで待ってから失敗する。短い上限で失敗させ、読み直しを促す |
| iframe の中の要素 | `iframe [ref=e3]` の下に `f1e2` の形で参照が付き、`aria-ref=f1e2` でクリックできた |
| パスワード欄 | スナップショットでは `textbox "pw"` で、ほかの入力欄と区別が付かない。参照で引いた要素の `type` 属性（`password`）で判定できる |
| 参照から要素の役割と名前を引く | `locator('aria-ref=e10').ariaSnapshot()` は `- button "送信する"` を返す。**ただし使えない**: Playwright は最後に取ったスナップショットの表で参照を引くため、要素だけのスナップショットを取ると表がその要素の分に置き換わり、元の参照が引けなくなる（実装の IT で、承認の後の操作が「見つからない」になって分かった）。ページ全体のスナップショットを取り直し、その中の参照の行（`- button "送信する" [ref=e10]`）から役割と名前を取る。変わっていない要素は同じ参照のまま残る |
| `confirm` | 今の作り（ダイアログを閉じる）では「キャンセル」になり、削除は行われなかった |
| `target="_blank"` のリンク | 新しいページ（`popup`）が開こうとする。今の作りではすぐ閉じる。`popup` のイベントは新しいページの最初の読み込みの応答の後（遅いページでは 1 秒近く後）まで来ない。読み込みのリクエストはクリックの直後に来る（フレームができる前のため `request.frame()` は例外を投げる） |
| 操作の後の待ち方 | `waitForLoadState('networkidle')` は文書ごとに 1 度しか待たず、すでに落ち着いた文書ではすぐ返る（操作が始めた `fetch`・新しいウィンドウを待たない）。コンテキストのリクエストを数え、進行中のものが無い状態が 500 ミリ秒続くまで待つ |

**モデルが参照で要素を指定できるか**

確認用のページを `browser_navigate` で開いた結果（参照付き）を渡し、操作のツール（案）で頼んだ。

| 頼んだこと | モデルの呼び出し | 結果 |
|---|---|---|
| 名前に「田中」、種別を「要望」、同意にチェックを入れて送信 | 1 回の応答で `browser_type(e5, 田中)`・`browser_select(e7, 要望)`・`browser_click(e9)` を**並べて**呼んだ（送信は結果を見てから。22.7 秒） | 参照はすべて正しい |
| 「項目 1」のボタンを押す（「項目 2」が前に並ぶ） | `browser_click(e16)`（12.3 秒） | 正しい（並びの順ではなく名前で選んだ） |
| 削除ボタンを押す | `browser_click(e13)`（6.1 秒） | 正しい |

- 参照で十分に指定できる。役割と名前で指定させる（同じ名前のボタンが並ぶと決まらない）必要はない。
- **1 回の応答で複数の操作を並べて呼ぶ**。今のループは並べて実行するため、同じページへの操作がぶつかる（[並んだ呼び出し](#並んだ呼び出し)）。

### Phase C の範囲

| 含める | 含めない（[Phase C のやらないこと](#phase-c-のやらないこと)） |
|---|---|
| クリック（ボタン・リンク・チェックボックス等）・文字の入力（入れた後の Enter を含む）・選択欄で 1 つ選ぶ | スクロール・キー操作・ホバー・ドラッグ・ファイルの添付 |
| 操作ごとの承認 | 一括の許可・承認の要らない操作 |
| 操作の後のページを読んで返す | ダイアログ（`confirm` 等）の受け入れ |
| 公開の Web と、許可した手元の開発サーバー（Phase A・B と同じ範囲） | パスワード欄への入力・ログインした状態を続けること |

### Phase C の決めること（レビューの論点）

| 論点 | 推奨 | 他の案 | 理由 |
|---|---|---|---|
| ツールの分け方 | **3 つ**: `browser_click`・`browser_type`・`browser_select` | Playwright MCP と同じく、キー操作・ホバー・ドラッグ・ファイルの添付まで入れる | 開発中の画面の確認（フォームに入れて送る・ボタンを押して表示を確かめる）は 3 つで足りる。増やすほどモデルが選び間違える。キー操作（Enter）は `browser_type` の `submit` で済ませる |
| 要素の指定 | **スナップショットの参照（`ref`）だけ** | 役割と名前（`button "送信"`）・CSS セレクタ | 調査でモデルは参照を正しく選んだ。参照は要素に結び付いてずれない。役割と名前は同じ名前の要素が並ぶと決まらず、セレクタはモデルが DOM を知らない |
| スナップショットの形 | **`browser_navigate`・`browser_snapshot` も参照付き（`mode: 'ai'`）に変える**。上限は 12,000 文字のまま | 操作のための参照付きの読み直しを別に用意する | 操作するには毎回参照が要る。読み直しを挟むとラウンドが 1 つ増える。文字数が 1.5 倍になり上限の中で読める量は減るが、続きは `offset` で読める |
| 承認の範囲 | **すべての操作で毎回承認**（クリック・入力・選択） | 手元の開発サーバーでは承認なし／クリックと送信付きの入力だけ承認 | ボタンが何をするかは押すまで分からない（送信・削除・購入）。入力も、打つたびに送るページ（検索の候補・自動保存）がある。手元の開発サーバーも、つながる先（開発用の DB・外部の API）を変えうる。`security.md` の「毎回の承認・一括の許可は作らない」に揃える。手間は、1 回の応答で並べて呼ばれた操作のカードが続けて出ることで抑える |
| 承認カードに出す要素 | **参照から引いた実際の要素**（役割と名前。`button "送信する"`）。モデルの説明（`element` の引数）は受け取らない | モデルの説明も出す（Playwright MCP の `element`） | ページの中の指示に従ったモデルが「保存ボタン」と書いて削除ボタンを指すと、説明が利用者を誤らせる。見せるのは実際に押すものだけにする |
| 承認と実行の間の変化 | **実行の直前に、ページの URL と要素の役割・名前が承認したときと同じか確かめ、違えば実行しない** | 確かめずに実行する | 承認を待つ間（最大 5 分）に、ページのスクリプトが要素を差し替えうる。ファイルの書き込みの「承認の間に変わっていれば書かない」と同じ考え方 |
| 並んだ呼び出し | **ブラウザのツールは、同じ応答の中で 1 つずつ、呼ばれた順に実行する**（ループに順に実行する仕組みを足す） | 並べたまま、ページの操作だけを順にする | 準備（承認カードの要素）を、前の操作が終わった後のページで作るため。並べたままだと、前の操作で消えた要素のカードを出しうる。承認カードは今も 1 枚ずつ出るため、利用者から見た流れは変わらない |
| 操作の結果 | **操作の後のスナップショットを返す**（`browser_navigate` と同じ形）。起きたこと（移った URL・閉じたダイアログ・開いた新しいウィンドウ・止めた接続）を前に書く | 「クリックしました」だけを返し、読むのは `browser_snapshot` に任せる | 押した結果を見るのがほぼ毎回のため、1 回で済ませる（ラウンドが 1 つ減る） |
| ダイアログ（`alert`・`confirm`・`prompt`） | **今までどおり閉じる（`confirm` はキャンセル）**。文言を結果に書く | 承認したクリックで出た `confirm` は受け入れる | クリックを承認した時点では、ダイアログの文言を利用者に見せていない。受け入れるなら、文言を見せて改めて承認を求める操作を別に作る |
| 新しいウィンドウ（`target="_blank"`・`window.open`） | ~~今までどおり開かずに閉じ、開こうとした URL を結果に書く~~ → **#200 で変更: 開いたままにし、以降の操作の対象にする（元のページは閉じる）**。[新しいウィンドウ](#新しいウィンドウ) | 同じページで開き直す | ページは 1 つに保つ（どのページを操作しているかを曖昧にしない）。最初は閉じていたが、動作確認で、リンクを押しても開かないのは分かりにくいと分かった。宛先の判定はプロキシが接続ごとに行うため、新しいウィンドウの読み込みも判定を通る |
| パスワード欄 | **入力を断る**（`input[type=password]`） | 入力できる | ツールの引数は会話の記録（DB）に残り、承認カードにも出る（#149 の「認証情報をツールの入力・ログに残さない」）。セッションは応答ごとの空のコンテキストで、ログインした状態を続けられない。ログインの要る確認は、会話をまたぐセッションと合わせて別に検討する |
| セッションの長さ | **応答ごとのまま** | 会話ごとに持つ | 1 回の応答の中で、開く → 操作する → 確かめる、まではできる。続けて頼む（「次はこれを押して」）ときは開き直しになるが、会話ごとにするには会話 ID の受け渡しと放置の後始末が要る。使ってみて要るとなってから |

### 操作のツール

3 つとも、[承認が要るツール](./15-tool-approval.md)（`prepare` を持つ）にする。準備で要素を確かめて承認カードの内容を作り、許可されたら操作して、操作の後のページを返す。この応答でまだページを開いていなければ、準備で失敗にする（「先に browser_navigate で開いてください」）。

#### `browser_click`

| 引数 | 必須 | 説明 |
|---|---|---|
| `ref` | ✓ | クリックする要素の参照（ページの内容の `[ref=e12]` の `e12`） |

#### `browser_type`

| 引数 | 必須 | 説明 |
|---|---|---|
| `ref` | ✓ | 入力欄の参照 |
| `text` | ✓ | 入れる文字（今の値は置き換える。5,000 文字まで） |
| `submit` | | 入れた後に Enter を押すなら true（検索欄・1 行のフォームの送信） |

- 入れられる要素: 文字の入力欄（`textbox`・`searchbox`・`spinbutton`、編集できる `combobox`）。それ以外・パスワード欄・無効（`disabled`・`readonly`）は準備で断る。
- Playwright の `fill`（1 文字ずつ打たず、値を置き換えて `input` イベントを出す）を使う。

#### `browser_select`

| 引数 | 必須 | 説明 |
|---|---|---|
| `ref` | ✓ | 選択欄（`<select>`）の参照 |
| `value` | ✓ | 選ぶ項目（表示の文字。スナップショットの `option "要望"` の `要望`） |

- 準備で、`<select>` であること・その項目があることを確かめる。複数選択は扱わない（1 つ選ぶ）。

#### 準備と実行

| 段階 | すること |
|---|---|
| 準備（`prepare`） | 参照の形（`e12`・iframe の中の `f1e3`）を確かめる → この応答で開いたページを取る → ページ全体のスナップショットを取り直し、参照の行から要素の役割と名前を引く（無ければ、`browser_snapshot` で読み直すよう返す） → ツールごとの確かめ（入力できる要素か・パスワード欄でないか・選択欄にその項目があるか） → 今のページが公開のページで、この応答で手元の情報を読んでいたら断る（[操作と外部への持ち出し](#操作と外部への持ち出し)） → 承認カードの内容を作る |
| 承認 | 承認カードを出し、利用者の許可を待つ（[15-tool-approval.md](./15-tool-approval.md) の流れのまま。待ち時間の上限 5 分） |
| 実行（`run`） | ページの URL と要素の役割・名前が準備のときと同じかを確かめる（スナップショットを取り直す。違えば実行せず、読み直しを促す） → 操作する（要素が操作できるまで待つ上限 5 秒） → 通信が落ち着くのを最大 2 秒待つ（進行中のリクエストが無い状態が 500 ミリ秒続くまで） → 起きたことと、操作の後のスナップショットを返す |

- 結果の要約（画面の 1 行）: `クリック: button "送信する"`・`入力: textbox "名前"`・`選択: combobox "種別" → 要望`。
- 結果の前置き（起きたことがあれば書く）:
  - ページが移った: `ページが移りました: <URL>`
  - ダイアログを閉じた: `ダイアログ（confirm）「本当に削除しますか？」をキャンセルしました`
  - 新しいウィンドウを開いた: `新しいウィンドウ（<URL>）を開きました。元のページは閉じ、以降はこのウィンドウを操作します`（#200 で変更。それまでは開かずに閉じていた）
  - 接続を止めた: `止めた接続: <宛先>`（プロキシの記録のうち、この操作の間のもの）

#### 承認カード

```ts
type BrowserActionApprovalPreview = {
  /** 何をするか。常に `browser-action` */
  action: 'browser-action';
  /** 操作の種類 */
  operation: 'click' | 'type' | 'select';
  /** 操作するページの URL とタイトル */
  url: string;
  title: string;
  /** 手元の開発サーバーのページなら true（公開のページか、手元かをカードに出す） */
  local: boolean;
  /** 操作する要素（参照から引いた役割と名前。`button "送信する"`） */
  element: string;
  /** 入れる文字（type）・選ぶ項目（select） */
  value?: string;
  /** 入れた後に Enter を押すか（type） */
  submit?: boolean;
};
```

- カードは「ページ（URL・タイトル・公開／手元）」「要素」「入れる文字・選ぶ項目」を出す。入れる文字は Markdown として描かずにそのまま見せる（GitHub のコメントの本文と同じ）。

### 並んだ呼び出し

- ツールの定義に、順に実行する組の名前（`exclusive: 'browser'`）を持たせる。ループは、同じ組のツールを、同じ応答の中で 1 つずつ、呼ばれた順に実行する（前の呼び出しの準備・承認・実行が終わってから次の準備に入る）。組を持たないツールは今までどおり並べて実行する。
- 6 つのブラウザのツール（読み取りの 3 つを含む）を同じ組にする。読み取りと操作が並んで呼ばれたときも、ページの状態が呼ばれた順に進む。
- 承認を拒否された・準備で失敗した呼び出しの後も、続きの呼び出しは進める（モデルは結果を見て次を決める）。

### 操作と外部への持ち出し

| ツール | 実行の前（止めるかの判定） | 実行の後（手元を読んだか。`readLocal`） |
|---|---|---|
| `browser_click`・`browser_type`・`browser_select` | 今のページが公開のページで、この応答で手元の情報を読んでいたら断る（ツールの準備で判定。引数だけでは決まらないため、ループの `access` は付けない） | 操作の後のページが手元の開発サーバーなら true |

- 公開のページへの入力は、入れた文字を外へ送りうる（`url_fetch` の URL に載せるのと同じ）。手元の情報を読んだ後は、プロキシも公開の Web へ接続しないが、ツールでも先に断って理由を返す。
- 手元のページのクリックで公開のページへ移る・公開のページのクリックで手元へ移る場合も、今までどおりプロキシが判定する（手元を読んだ後は公開の Web へ接続しない。公開のページからは手元へ接続しない）。

### Phase C の上限値

| 項目 | 値 | 理由 |
|---|---|---|
| 要素が操作できるまで待つ時間 | 5 秒 | 表示・有効になるのを待つ。ツール全般の上限（30 秒）の中に、落ち着くのを待つ時間とスナップショットを収める |
| 操作の後、通信が落ち着くのを待つ時間 | 最大 2 秒（進行中のリクエストが無い状態が 500 ミリ秒続いたら終わる） | 上限は `browser_navigate` と同じ。500 ミリ秒は Playwright の `networkidle` と同じ |
| 入れる文字 | 5,000 文字 | フォームの入力には足りる。承認カードで読める量にする |

### Phase C の脅威と対策

| 脅威 | 対策 |
|---|---|
| ページの中の指示で、モデルが意図しない操作をする（削除・送信・購入） | 毎回の承認。カードには、モデルの説明ではなく参照から引いた実際の要素を出す |
| 承認の間にページが要素を差し替える | 実行の直前に、URL と要素の役割・名前が承認したときと同じか確かめる |
| 手元の情報を公開のページのフォームに入れて送る | 手元の情報を読んだ後は、公開のページの操作を断る。プロキシも公開の Web へ接続しない |
| 認証情報を会話の記録に残す | パスワード欄への入力を断る |
| このアプリ自身の承認カードを押させる | このアプリのオリジンは開けない（Phase A・B のまま） |
| `confirm` で確かめる操作を、確かめずに進める | ダイアログはキャンセルし、文言を結果に書く |
| 新しいウィンドウで判定を通らないページを開く | 新しいウィンドウの読み込みも、ほかの通信と同じくプロキシが接続ごとに判定する（開く前のページを最上位として判定するため、公開のページから開いたウィンドウは手元の開発サーバーへ接続できない。手元を読んだ後は公開の Web へ接続しない） |

### Phase C のファイル構成

```
front/src/lib/agent/tools/browser/
├── element.ts   # 参照の形の確かめ・スナップショットを取り直して参照の行を探す・役割と名前を引く
├── action.ts    # 操作のツールに共通の準備と実行（開いたページ・外部への持ち出し・承認カード・起きたことの記録・操作の後のスナップショット）
├── click.ts     # browser_click
├── type.ts      # browser_type
└── select.ts    # browser_select
```

- `snapshot.ts`: スナップショットを参照付き（`mode: 'ai'`）にする。
- `session.ts`: ダイアログを閉じたこと・新しいウィンドウを開いたことを記録し、操作の結果に書けるようにする（新しいウィンドウは最初の読み込みのリクエストで記録する）。コンテキストのリクエストを数えて、通信が落ち着くのを待つ（`waitForQuiet`）。
- `types.ts`: `prepare` に応答ごとの文脈（`ToolContext`）を渡す。順に実行する組（`exclusive`）を足す。
- `agent.ts`: 同じ組のツールを順に実行する。`prepare` に文脈を渡す。
- `types/agent/tool-call.ts`: `BrowserActionApprovalPreview` を `ApprovalPreview` に足す。
- `ApprovalCard`: `browser-action` のカード。
- `registry.ts`: `BROWSER_ENABLED` のとき、読み取りの 3 つと合わせて 6 つを登録する。
- `constants/chat/toolLabels.ts`: 3 つのツールの表示名。

### Phase C のテスト

| 層 | 対象 |
|---|---|
| UT | 参照の形・スナップショットから参照の行を探す・要素の行（`- button "送信する"`）から役割と名前を取る・入れる文字と選ぶ項目の検証（上限・型）・承認カードの内容・結果の前置き（起きたこと）・外部への持ち出しの判定 |
| IT | 実際の Chromium と手元の HTTP サーバー、`/api/chat`（Ollama はスタブ）と承認の API で: クリックで表示が変わり、操作の後のスナップショットが返る・入力して `submit` で送る・選択欄で選ぶ・拒否したら操作しない・承認の間に要素が変わったら操作しない・消えた参照は承認を求めずに失敗・パスワード欄は承認を求めずに断る・`<select>` でない要素・無い項目は断る・`confirm` はキャンセルして文言を返す・`target="_blank"` は閉じて URL を返す・1 回の応答で並べた 2 つの操作が順に承認を求める（2 つ目の承認の要求は 1 つ目の結果の後）・まだ開いていなければ失敗 |
| E2E | `GET /api/tools` に 3 つが出る（CI でも動く）。大きいモデルで、確認用のページのボタンを押させる → 承認カードに要素が出る → 許可すると押した後の表示を答える・拒否すると押さない（`IS_LIGHT_MODEL` でスキップ） |

- 確認用のページ（`tests/e2e/fixtures/browser/`）に、押すと表示が変わるボタンを足す。

### Phase C のやらないこと

- **スクロール・キー操作・ホバー・ドラッグ**: クリックは要素まで自動でスクロールする。スクリーンショットで下の方を見たい・メニューをホバーで開くなどが要るとなってから足す。
- **ファイルの添付**（`<input type="file">`）: 手元のファイルをページへ渡すことになり、ローカルのファイルのツールの許可（フォルダ・秘匿ファイル）と合わせて考える必要がある。
- **ダイアログの受け入れ**: 文言を見せて承認を求める操作として、要るとなってから。
- **パスワード欄・ログインした状態を続けること**: 会話をまたぐセッションと合わせて検討する。

## 画面をチャットに出す

ブラウザのツールが開いた・操作した画面のスクリーンショットを、チャットの中で利用者に見せ、会話に保存する（#149。サブ issue #200）。Phase C までは、チャットに出るのは「開いた」「入力した」「選んだ」という文字だけで、利用者は画面を見られなかった。承認カードでも、要素の役割と名前（`button "送信する"`）だけでは、画面のどこを操作するのか分かりにくい。

### 画面の表示の前提の調査

Playwright 1.64.1 で確かめた（2026-10-30。表示の大きさは 1,280×800）。

| 確かめたこと | 結果 |
|---|---|
| 画像の大きさ | 確認用のページで PNG 40KB・JPEG（品質 70）26KB、`example.com` で PNG 81KB・JPEG 50KB。文字の多いページ・写真のあるページでは数百 KB になりうる |
| 要素の位置 | `locator.boundingBox()` は、見えている範囲の左上からの位置（px）を返す。画面の外の要素は範囲の外の値になる（下へ 2,000px の要素で `y: 2138`） |
| 画面の外の要素 | `scrollIntoViewIfNeeded()` の後は範囲の中の値になる（`y: 438`）。表示の倍率は 1 のため、位置はスクリーンショットの画素と一致する |

### 画面の表示の範囲

| 含める | 含めない（[画面の表示のやらないこと](#画面の表示のやらないこと)） |
|---|---|
| 操作の承認カードに、操作する要素を枠で囲んだ画面を出す | 動画・連続した画面の中継 |
| 操作・`browser_navigate` の後の画面を、ツールの結果に出す | `browser_snapshot` の画面（読み直しは画面が変わらないため） |
| `browser_screenshot` がモデルへ渡した画像を、ツールの結果に出す | 画面の画像をモデルへ渡すこと（`browser_screenshot` のほかは今までどおり渡さない） |
| 会話に保存し、開き直しても見られる | エクスポートに画像の中身を入れること |

### 画面の表示の決めること（レビューの論点）

| 論点 | 推奨 | 他の案 | 理由 |
|---|---|---|---|
| どの画面を出すか | **操作の前（承認カード）・操作の後・`browser_navigate` の後・`browser_screenshot`** | 操作の後だけ | 承認するときに「どこを押すか」を見せるのが一番効く。開いた直後の画面も、何を開いたかを確かめるのに要る。`browser_screenshot` は、モデルが見た画像を利用者も見られるようにする |
| 要素の示し方 | **要素の位置（`box`）を画像と別に持ち、画面で枠を重ねて描く** | ページに枠の要素を差し込んでから撮る／サーバーで画像に枠を描く | ページの DOM を書き換えない（ページのスクリプトが差し込んだ要素に反応しうる）。画像を加工するライブラリを入れずに済む。枠は位置の値から描くため、拡大しても崩れない |
| 画面の外の要素 | **撮る前に、要素が見えるところまでスクロールする** | スクロールせず、枠なしで撮る | 押すものが写っていないと、カードの画像が役に立たない。承認の前にページへ起こす変化はスクロールだけで、操作（クリック）も同じスクロールをする |
| 画像をモデルへ渡すか | **渡さない**（`browser_screenshot` だけ今までどおり渡す） | 操作の後の画面も渡す | 1 枚 約 900 トークン・約 8 秒かかる（`docs/13-image-attachment.md`）。操作の結果はスナップショットの文字で返しており、モデルは画像を要しない。画像を読めないモデルでも画面を出せる |
| 画像の形式 | **JPEG（品質 70）**。`browser_screenshot` はモデルへ渡した PNG をそのまま出す | すべて PNG | 調査で JPEG は PNG の 6 割程度。見るための画像には足りる。`browser_screenshot` は、モデルが見たものと同じ画像を見せる |
| 保存先 | **今の添付画像（`Attachment`）に、assistant のメッセージの画像として保存する**。応答の保存のときに、画面（クライアント）が画像を一緒に送る | 新しいテーブル／`metadata` の JSON に Base64 で入れる／サーバーが撮った時点で保存する | 会話の削除でカスケード削除され、形式の判定（マジックナンバー）と配信の API（`/api/attachments/[id]`）をそのまま使える。JSON に入れると、メッセージの一覧の取得が画像の中身ごとになる（#6 と同じ理由）。応答の保存はもともと画面が行う（ID・再生成の置き換え・保存の再試行）。サーバーが先に保存すると、保存しなかった応答（本文の無い応答・生成中に消した会話）の画像が残る |
| 1 回の応答で撮る枚数 | **20 枚まで**。超えたら撮らない（結果の文章は変わらない） | 上限なし | 操作 1 回で 2 枚（前・後）のため、操作 10 回分。保存の API のボディが際限なく大きくならないようにする（JPEG で数 MB） |
| 結果に出す場所 | **ツールの結果のパネルの下に、パネルの幅いっぱいの画像を縦に並べて出し、押すと拡大する**（折りたたまない。承認カードもカードの幅いっぱい） | 結果のパネルを開いたときだけ出す／小さいサムネイルを横に並べる | 利用者が見たいのは画面そのもの。開かないと見えないと、今の「文字だけ」と変わらない。最初は高さ 120px のサムネイルにしたが、動作確認で画面の文字が読めなかったため、幅いっぱいにした |
| 拒否・失敗したとき | **操作の前の画像（承認カードの画像）は結果にも残す。操作の後の画像は、操作を試みた後にページが残っていれば撮る** | 成功したときだけ残す | 何を断ったか・どこで失敗したかを、後から見て分かるようにする |

### 画面の表示の作り

**型**

```ts
/** ツールが撮った画面のスクリーンショット（#200）。`metadata.toolCalls[].screenshots` に保存する */
type ToolScreenshot = {
  /** 添付画像の ID（サーバーが採番し、保存でもこの ID を使う） */
  id: string;
  /** 操作の前（承認カード）か、操作・ページを開いた後か */
  kind: 'before' | 'after';
  /** 形式（操作・開いた後は JPEG、browser_screenshot は PNG） */
  mimeType: 'image/jpeg' | 'image/png';
  width: number;
  height: number;
  /** 操作する要素の位置（画像の左上からの px。before だけ。要素が見えなければ省く） */
  box?: { x: number; y: number; width: number; height: number };
};
```

- `ToolCallInfo` に `screenshots?: ToolScreenshot[]` を足す（保存する記録には中身を入れない）。
- 中身（Base64）は、ストリームのイベントだけが運ぶ: `BrowserActionApprovalPreview` の `screenshot`（承認カードの画像）と、`tool_call_result` の `screenshots`（`ToolScreenshot` と `data`。操作の前の画像も入れ直す。画面が承認カードと結果を突き合わせずに済むように）。`done` の `toolCalls` は中身を持たない。
- ツールの実行結果（`ToolExecution`）に `screenshots` を足し、ループがイベントへ載せ、記録からは中身を外す。準備で撮った操作の前の画像は、承認の結果（許可・拒否・時間切れ）にかかわらず記録に入れる。

**撮る**

- `browser/capture.ts`（新規）: 開いたページを JPEG で撮り、ID を付ける。要素を渡すと、`scrollIntoViewIfNeeded()` の後に `boundingBox()` を取り、画像の範囲に収めて `box` にする。1 回の応答で撮った枚数を応答ごとの文脈（`scope`）で数え、上限を超えたら撮らない。撮れなかった（時間切れ等）ときも、ツールの結果は失敗にしない。
- `action.ts`: 準備（`prepare`）で操作の前を撮ってカードに載せ、実行（`run`）の後に操作の後を撮る。
- `navigate.ts`: 開いた後を撮る。`screenshot.ts`: モデルへ渡す PNG を、そのまま `screenshots` にも入れる。

**保存と読み込み**

| 対象 | 変更 |
|---|---|
| `POST /api/conversations/[id]/messages` | assistant も `attachments` を指定できる（上限 `MAX_TOOL_SCREENSHOTS_PER_MESSAGE` = 20 枚。user は今までどおり 4 枚） |
| `PUT /api/conversations/[id]/messages/[messageId]`（再生成） | `attachments` を受け取り、古い応答の画像を消して作り直す（同じトランザクション） |
| `GET /api/conversations/[id]/messages` | 変更なし（assistant の画像の情報も返る） |
| 画面（`useChat`） | 届いた中身を記録の ID ごとに持ち、表示は `data:` の URI、保存のときに `attachments` として送る。読み込んだ会話は `/api/attachments/[id]` で表示する。添付画像（`images`）として扱うのは user のメッセージの画像だけにする（assistant の画像を履歴の `imageIds` に入れない） |
| `metadata` の読み込み | `toolCalls[].screenshots` を検証し、形の合わないものは捨てる（DB の JSON は信用しない） |

- DB のスキーマは変えない（`Attachment` のコメントを「user の添付と、ツールのスクリーンショット」に直す）。
- 会話の履歴としてモデルへ送るのは今までどおり本文だけで、スクリーンショットは送らない。

**表示**

- `ToolScreenshots`（新規・`features/chat/molecules`）: 置かれた欄の幅いっぱいに画像を縦に並べ（操作の前と後があれば、画像の上に見出し）、`box` があれば枠を重ねる。押すと拡大し、拡大でも枠を重ねる。
- `ElementBoxOverlay`（新規・`features/chat/atoms`）: 画像と同じ領域に SVG を重ね、`viewBox` を画像の画素にして枠を描く。収め方（`preserveAspectRatio`）を画像と揃える（サムネイルは `none`、拡大は `object-contain` に合わせて `xMidYMid meet`）ため、位置を割合に直す計算が要らない。線の太さは `vector-effect: non-scaling-stroke` で画面の px に保つ。
- `ApprovalCard`（`browser-action`）: 要素の行の上に、操作の前の画像を枠付きで出す。
- `ToolCallResult`: パネルの下に `ToolScreenshots` を出す。

### 画面の表示の上限値

| 項目 | 値 | 理由 |
|---|---|---|
| JPEG の品質 | 70 | 調査で PNG の 6 割程度。文字は読める |
| 1 回の応答で撮る枚数 | 20 枚 | 操作 10 回分。保存のボディを数 MB に収める |
| 1 枚の大きさ・縦横 | 今の添付画像と同じ（5MB・長辺 1,280px） | 表示の大きさ（1,280×800）は長辺 1,280px に収まる |

### 画面の表示の脅威と対策

| 脅威 | 対策 |
|---|---|
| ページの中の秘匿の情報が、画像として会話に残る | 今もスナップショットの文字が結果として残っている。セッションは応答ごとの空のコンテキストで、利用者のログインした状態は写らない。パスワード欄には入れない（入れた文字は伏せ字のまま写る） |
| 画像に見せかけたファイルを保存させる | 保存では今までどおり中身の先頭で PNG / JPEG を判定し、配信は判定済みの `Content-Type` と `nosniff` で返す |
| 枠の位置を偽って、別の要素を押させる | 位置はモデルではなく、参照から引いた要素から取る。透明な要素を上に重ねた場合は、Playwright のクリックが「要素が操作を受けられるか」を確かめて失敗する |
| 承認の前のスクロールで、ページが動く（遅延の読み込み・スクロールの検知） | 変化はスクロールだけで、クリックも同じスクロールをする。カードの画像はスクロールの後の画面になる |
| 画像が大きく、保存・表示が重くなる | JPEG・1 回の応答で 20 枚まで |

### 新しいウィンドウ

Phase C では新しいウィンドウを開かずに閉じていたが、動作確認で「リンクを押しても開かない」のは分かりにくいと分かったため、#200 で変えた（利用者の指示）。

- 操作で新しいウィンドウ（`target="_blank"`・`window.open`）が開いたら、閉じずに開いたままにし、以降の操作・読み直し・スクリーンショットの対象をそのウィンドウに切り替える。元のページは閉じる（操作するページは 1 つに保つ）。
- 新しいウィンドウにも、ダイアログを閉じる・最上位のページを追う・さらに開いたウィンドウを引き継ぐ、の扱いを付ける（`session.ts` の `watchPage`）。
- 新しいウィンドウの最初の読み込みは、開く前のページを最上位としてプロキシが判定する。公開のページから開いた手元の開発サーバーのウィンドウは接続できず、エラーのページになる（結果に止めた接続を書く）。
- 操作の結果は、新しいウィンドウを読んで返す（`URL:` は新しいウィンドウの URL）。操作の後の画面（#200）も新しいウィンドウを撮る。
- `window.open()` で空のウィンドウを開いてから移る場合は、記録（「新しいウィンドウを開きました」）の代わりに「ページが移りました」と書く（空のウィンドウを開いた時点で操作の対象を切り替えるため）。

### 画面の表示のやらないこと

- **動画・画面の中継**: 操作の前と後の静止画で、何をしたかは追える。連続した画面が要るとなってから。
- **画面に出して動かす（headed）**: サーバーで動く Chromium の窓を利用者の画面に出すのは、ヘッドレスで動かす今の作り（CI・複数の応答）と合わない。
- **エクスポートに画像を入れる**: 今の添付画像と同じく、ID と大きさだけを入れる。

## やらないこと

- **クリック・入力・選択**: Phase C（[Phase C: 操作のツール](#phase-c-操作のツール)）で入れる。スクロール・キー操作・ホバー・ドラッグ・ファイルの添付・ダイアログの受け入れは、Phase C でも入れない（[Phase C のやらないこと](#phase-c-のやらないこと)）。
- **会話をまたぐセッション・ログイン**: Phase C でも入れない。1 回の応答の中で、開く → 操作する → 確かめる、まではできる。
- **画面に出して動かす（headed）**: 動作を見たいとなれば環境変数で切り替える。
- **スクリーンショットの表示・保存**: [画面をチャットに出す](#画面をチャットに出す)（#200）で入れる。
- **Chromium 以外のブラウザ**: E2E と同じ Chromium だけにする。
